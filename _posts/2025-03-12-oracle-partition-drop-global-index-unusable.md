OAM(통합인증) 프로젝트에서 파티션 테이블을 다루다가 겪은 일을 정리해둔다. **오픈 전 검증(가동계 테스트) 단계**에서 일어난 일이라 실제 서비스 이용자에게 영향은 없었지만, 로그인을 처리하는 시스템이다 보니 검증 중 로그인 자체가 막히는 상황이 됐다.

## 1. 사고 경위

문제가 된 테이블은 직접 설계한 테이블이 아니라 **OAM 솔루션 자체가 제공하는 테이블**이었다. 이런 솔루션 테이블은 보통 앞으로 필요한 파티션을 사람이 미리 만들어두는 게 아니라 `DBMS_JOB`으로 등록된 스케줄러가 주기적으로 다음 파티션을 알아서 미리 생성해두는 구조다.

오래된 파티션을 정리하는 드롭 테스트를 신입 개발자에게 맡겼는데, 대상 범위를 잘못 지정해서 **현재월부터 미래월까지의 파티션이 통째로 드롭돼버렸다.** 원래 정리 대상은 지나간 과거 파티션이었는데, 정작 지금 들어오는 데이터가 들어갈 당월 파티션과 `DBMS_JOB`이 미리 만들어둔 미래 파티션까지 다 날아간 것이다.

## 2. 에러가 두 번 바뀌었다

처음 로그인 실패 로그를 열어보니 이 에러였다.

```
ORA-14400: inserted partition key does not map to any partition
```

당월 데이터를 써야 하는데 그 값을 담을 파티션 자체가 없으니, INSERT 시점에 "이 값을 넣을 파티션을 못 찾겠다"고 거부당한 것이었다. 원인이 명확해서, 과거~미래 구간의 파티션을 스크립트로 다시 생성했다.

그런데 파티션을 만들었는데도 로그인이 여전히 안 됐다. 로그를 다시 보니 이번엔 **다른 에러**로 바뀌어 있었다.

```
ORA-01502: index 'SCHEMA.IDX_NAME' or partition of such index is in unusable state
```

인덱스가 UNUSABLE 상태라는 오류였다. 파티션 드롭 작업이 그 테이블에 걸려있던 글로벌 인덱스를 깨뜨려놨던 것이다. 파티션을 새로 만든다고 그때 이미 깨진 인덱스가 저절로 복구되는 게 아니었다.

글로벌 인덱스는 파티션 구조와 무관하게 테이블 전체를 하나로 묶은 인덱스라, `DROP PARTITION` 같은 파티션 단위 작업이 일어나면 (`UPDATE INDEXES` 옵션 없이는) 인덱스 전체가 UNUSABLE 상태로 빠진다. 드롭된 파티션이 몇 개든 상관없이 인덱스는 통째로 깨진다.

## 3. 조치: 인덱스 리빌드

```sql
ALTER INDEX idx_name REBUILD ONLINE PARALLEL NOLOGGING;
```

인덱스를 리빌드하고 나서야 로그인이 정상적으로 됐다. 파티션 문제 하나만 보고 있다가, 그걸 고치니 곧바로 또 다른 에러(인덱스)가 튀어나와서 "파티션을 살렸는데 왜 또 안 되지"하며 잠깐 헤맸다 — 파티션 드롭이 인덱스까지 건드린다는 걸 그 자리에서 체감했다.

## 4. 이후 대응

사실 이 사고가 있기 전, DB 인수 점검 때 이 테이블에 글로벌 인덱스 대신 로컬 인덱스를 쓰라는 권고를 받은 적이 있었다. 그런데 오라클 엔지니어가 "솔루션에서 생성한 테이블은 나름의 이유가 있을 수 있으니 함부로 건드리지 않는 게 좋다"고 해서, 당시엔 그 권고를 반영하지 않고 그대로 뒀다. 이번 사고를 직접 겪고 나서야 왜 로컬 인덱스를 쓰라고 했는지 몸으로 이해하게 됐다.

이 사고 이후로 파티션 테이블에 인덱스를 잡을 때는 가능한 한 로컬 인덱스를 우선 검토하게 됐다. 로컬 인덱스는 테이블 파티션과 1:1로 대응돼서, 특정 파티션이 드롭돼도 그 파티션에 해당하는 인덱스 조각만 같이 없어질 뿐 나머지는 멀쩡하다. 부득이하게 글로벌 인덱스를 써야 한다면, 파티션 작업 시 `UPDATE INDEXES` 절을 같이 써서 애초에 UNUSABLE 상태로 빠지지 않게 하는 것도 방법이다.

그리고 파티션처럼 데이터 구조 자체를 바꾸는 작업은 테스트할 때 영향 범위(이번 경우엔 "당월·미래 파티션까지 드롭 대상에 포함되는지")를 사전에 한 번 더 리뷰하는 절차가 필요하다는 것도 같이 배웠다.
